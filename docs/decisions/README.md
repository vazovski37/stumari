# Architecture Decision Records

Short records of decisions that shape the MVP. Status is **Accepted** unless noted. Change a decision by adding a new ADR that supersedes it.

## ADR-0001 — Monorepo, TypeScript app + Anchor program + Python training
**Context:** two founders, 17 days, one deployable web product. **Decision:** pnpm workspace (`apps/web`, `apps/mcp`, `packages/core`), Anchor 1.1.2 workspace in `onchain/`, Python in `ml/`. One Next.js app holds landing, checkout, dashboard, admin and API routes (single Vercel deploy). **Consequence:** shared TS logic lives in `packages/core`; the program is built in WSL (ADR-0008).

## ADR-0002 — Full prepay into escrow (no partial deposits in the MVP)
**Context:** partial deposits need a second payment rail at the property and complicate the demo. **Decision:** the escrowed amount is the full price; `deposit_bps = 10000` stays in the quote format. **Consequence:** the model's levers are price and contract template, not deposit %. Partial deposits are a pure off-chain change later (the program already escrows any `amount`).

## ADR-0003 — Menu of templates priced by risk, instead of a bandit policy
**Context:** a Thompson-sampling bandit needs traffic we do not have and is hard to explain on a sales call. **Decision:** three fixed templates (flexible / standard / non-refundable). The hotel's reference template always costs its base rate; the others are priced so that, for *this* request, every option earns the same expected revenue as the reference (per-request anchor; no credit for resale when nothing is refunded — pricing-and-risk-model.md §5). **Consequence:** deterministic, explainable, testable; the bandit can later choose which templates to show and the reference price.

## ADR-0004 — Quote signer co-signs `create_booking` (no Ed25519 instruction introspection)
**Context:** terms must be authenticated on-chain. Options: verify an Ed25519 precompile instruction via the instructions sysvar, or require the quote signer as a transaction signer. **Decision:** co-signing. The server builds the transaction, so it can sign it; every argument is covered by the signature. **Consequence:** simpler program, no parsing of precompile data; the off-chain quote carries its own Ed25519 signature for agents, and `quote_hash` links the two.

## ADR-0005 — iCal first; Channex and PMS adapters later
**Context:** Tbilisi independents list on Booking.com/Airbnb and often have no channel manager. **Decision:** iCal import/export per unit + manual blocks; bookings start `Pending` until a fresh re-sync confirms no conflict. **Consequence:** 15-minute onboarding without partnerships; small double-booking window handled by confirm/void.

## ADR-0006 — Single admin key as arbiter stub (disclosed)
**Decision:** disputes are resolved by `config.admin`. Shown on screen and in docs as a stub; roadmap is a Squads multisig of bonded arbiters. **Consequence:** fast MVP; the trust property (escrow only to guest/hotel/treasury) limits the damage.

## ADR-0007 — GBDT hazard model exported to JSON, evaluated in TypeScript
**Context:** ONNX Runtime in a serverless Next.js function is heavy; a Python microservice is a second deployable. **Decision:** LightGBM with numeric-only features (one-hot categoricals), exported to a compact JSON tree format + isotonic table; a ~100-line TS evaluator in `packages/core`, verified against Python on parity vectors. **Consequence:** zero runtime dependencies, sub-millisecond scoring, identical results in browser, server and MCP.

## ADR-0008 — Build the program in WSL on a native filesystem
**Context:** Anchor/Solana toolchain is Linux-first; building on `/mnt/c` is slow. **Decision:** `scripts/program.sh` rsyncs `onchain/` to `~/stumari-onchain` inside WSL Ubuntu 24.04, runs `anchor build` / `cargo test` there, and copies `target/deploy/*.so`, `target/idl/*.json` back to `onchain/artifacts/`. **Consequence:** fast incremental builds; the repo holds the IDL the TS client is generated from. **Program id is fixed:** `6Y17gFD9dWPJF6GtpzABJZY7Pk8j5CLh268zZyW5U6nf`, recorded in `onchain/artifacts/program-id.txt` (committed). The keypair (`onchain/keys/`, gitignored) is shared between founders out of band (password manager), never committed; `STUMARI_PROGRAM_ID` must equal program-id.txt (checked at web startup).

## ADR-0009 — Server builds every transaction; browser only signs (gasless)
**Context:** Kit 8 + wallet plugins are new; guests (card-blocked tourists) may hold USDC but no SOL. **Decision:** API returns base64 v0 transactions with the operator as fee payer (and rent payer); the browser signs via Wallet Standard (`solana:signTransaction`) and posts back for relay. A devnet-only demo wallet (local keypair + faucet) signs the same bytes. **Consequence:** no program client or RPC in the browser — it uses Wallet Standard directly (`@wallet-standard/app`, feature `solana:signTransaction`: bytes in, bytes out) plus `@solana/kit` codecs; guests need only USDC; judges and hotel prospects can try the live product without installing Phantom. **Demo wallet:** 32 random bytes in `localStorage['stumari_demo_sk']` (devnet only, labelled "Test wallet — devnet, not real money"), `createKeyPairSignerFromPrivateKeyBytes`, signs the decoded server-built transaction and merges its signature; a "Get 500 test USDC" button calls `/api/demo/faucet`; rendered only when `/api/config/public.demo_mode` is true.

## ADR-0010 — Kit 8 + Codama client on the server, transaction version 0
**Context:** `@solana/kit` 8 with Codama clients is the maintained stack (Sep 2026); v1 transactions are live on mainnet but not all wallets sign them. **Decision:** generate a Kit client for `stumari_escrow` from the Anchor IDL with Codama; build **v0** transactions (all ours fit in 1232 bytes). **Consequence:** widest wallet compatibility now; switching to v1 later is a one-line change.

## ADR-0011 — One booking per quote (deterministic booking id)
**Context:** retries of `/pay` with random booking ids let one quote create several escrows (double charge). **Decision:** `booking_id = sha256("stumari-booking-v1" ‖ quote.id)[0..16]`; the `init` of the booking PDA makes a second `create_booking` for the same quote fail on-chain. **Consequence:** idempotent payment; the server returns `409 ALREADY_PAID` once the account exists.

## ADR-0012 — Snapshot payout owner and fee on each booking; guest-protected cancel
**Context:** the design review found that `update_hotel(authority)` could redirect open bookings' payouts, and that a confirm race or tier boundary could silently cut a guest's refund. **Decision:** `Booking.hotel_authority` and `Booking.fee_bps` are fixed at creation; `cancel_booking(min_refund)` fails rather than refunding less than the guest was shown; `confirm_booking` only before `confirm_deadline_ts`; `flag_dispute` only between check-in and release; vault excess is swept to the treasury so a donation can never block closing. **Consequence:** the trust property holds for every booking regardless of later admin actions.

## ADR-0013 — What we promise hotels (and what we do not)
**Context:** sales calls and the landing page must not promise features the MVP lacks. **Decision:** the single source is `docs/sales/offer.md`. We promise: USDC on Solana paid to a wallet the hotel controls, released automatically 24 h after check-in unless the guest opens a dispute (decided by our disclosed arbiter); guest refunds follow the chosen schedule automatically; guests need no SOL; 0% fee until 2026-12-31 then 1.5%, written into each booking; per-booking cap 1,500 USDC during the pilot. We do not promise: GEL payouts or conversion (we help them find a licensed provider), any token other than USDC on Solana, new demand, legal/tax compliance, guaranteed revenue ("priced to target your current expected revenue"), exchange deposit addresses as payout wallets, or iCal onboarding for multi-unit room types before checking their extranet.

## ADR-0014 — Agents are priced as direct buyers; model features trimmed for honesty
**Context:** the pricing review trained the spec model on the real data. Online TA bookings cancel 2.6× more than Direct in the prior, so mapping AI agents to "Online TA" would make every agent quote visibly worse; `previous_cancellations`, `adr` and `arrival_week` are artifacts or do not transfer. **Decision:** agents map to Direct/Direct (an agent acting for its own user is a direct booking; `buyer_type` is still shown in the explain block); the model drops `previous_cancellations`, `adr`, `arrival_week`, trains only on the No-Deposit population, and uses monotone constraints on wallet history. **Consequence:** expected booking-level AUC ≈ 0.71 vs 0.64 for lead time alone — presented as modest but calibrated; multipliers are independent of the base rate.

## ADR-0015 — Local chain = Surfpool in Docker
**Context:** on this Windows machine, ports inside WSL are not reachable from Windows (neither `localhost` nor the WSL IP), while Docker Desktop's published ports are. The web app, scripts and tests run on Windows Node. **Decision:** `scripts/localnet.sh start|stop|status|logs|reset` runs the Linux `surfpool` 1.6 binary (copied from WSL into `.localnet/bin/`, gitignored) inside an `ubuntu:24.04` container on `http://127.0.0.1:8899` (ws 8900), offline. Programs are deployed with the `surfnet_writeProgram` cheatcode (with the operator as upgrade authority), the clock moves with `surfnet_timeTravel`, SOL/token balances with `surfnet_setAccount` / `surfnet_setTokenAccount`. Anchor builds and the Rust LiteSVM tests stay in WSL (ADR-0008). **Consequence:** no firewall or WSL networking changes on the host; the whole E2E runs from Windows.

## ADR-0016 — Platt scaling instead of isotonic calibration
**Context:** isotonic calibration of the raw margin is a step function: on the parity requests, 178 reachable windows mapped to only 19 distinct hazards, so nearby requests shared identical prices and prices jumped at step edges. **Decision:** export Platt scaling `hazard = 1/(1+exp(-(a·raw+b)))` fit on validation raw margins (a ≈ 1.04, b ≈ 0.08 — the GBDT was already close to calibrated); keep isotonic in both evaluators and in the report for comparison. **Consequence:** smooth, strictly monotone prices (112 distinct hazards on the same requests); test AUC 0.713 (isotonic ties had lowered it to 0.709); expected calibration error 0.038 vs 0.029 for isotonic and 0.041 uncalibrated — a small, disclosed cost. Parity: `raw` exact, `hazard` within 1e-12 (only `exp` may differ by an ulp between Python and V8).
